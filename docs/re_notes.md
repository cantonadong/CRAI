# Null's Royale 逆向笔记

## 目标构建
| 项目 | 值 |
|---|---|
| 包名 | `nullsroyale.rel.free` |
| versionName / versionCode | 16.635.1 / 160635001 |
| 安装 ABI | `arm64-v8a`（APK 内只有 arm64-v8a、armeabi-v7a，**没有 x86_64**） |
| libg.so（arm64）SHA-256 | `0B580222E5A3502CF153BB5E6297EC32D2B154B605B777C74873DD75722E4EAA` |
| libg.so 大小 | 29,408,752 字节 |
| 运行环境 | LDPlayer9，Android 9（SDK 28），native bridge `libnb.so`（ARM 转译） |

参考文档 `refs/cr-memory-reader/x86_64/内存读取技术指南.md` 针对的是 x86_64 版 libg.so，**它的函数和全局变量偏移不能用于本构建**。对象内的字段布局可以作参考，但要逐项重新验证。

## 运行时（已验证 2026-11-20）
- 游戏进程里 libg.so 以 ARM64 镜像映射在低地址，例如基址 `0x030c8000`，每次启动会变。
  - 运行时地址 = 基址 + 静态偏移。
  - 可读写的数据段：文件偏移 `0x1a99000` 起。
- root 下可以用 `dd if=/proc/<pid>/mem` 读取内存，已读到 ELF 文件头 `7f 45 4c 46`。
- 代码段映射为 `r--p`，因为执行的是转译后的代码，所以 Frida 或 inline hook 不可行。只走读内存这条路。

| 下一张牌队列位置 | — | 推测在 `player+0x200`，即数据指针 `+0x220`、数量 `+0x22c` | **待实战验证** |

## 实战验证（2026-11-20，训练赛）
工具：`crai/reader/scan_player.c`（扫描候选对象）、`crai/reader/watch_player.c`（监视已知地址）。两者都用 NDK `x86_64-linux-android28-clang` 编译，root 下运行。

- 扫描结果中，有 2 个候选对象的"手牌 4 张 + 队列 4 张"正好覆盖 0–7，这就是双方的 runtime player。
  - 地址在高位堆区，例如 `0x7638514f6800`。每局都不同，不能写进配置。
- 15 秒连续读取，以下字段**全部确认**：

| 字段 | 偏移 | 说明 |
|---|---|---|
| 原始圣水 | `+0x2f8` i32 | 除以 10000；回费约 0.36/s，下牌时按费用扣减 |
| 手牌数组指针 | `+0x210` → i32[4] | 值是 deck index 0–7；出牌瞬间该槽会短暂为 `-1`，要过滤 |
| 手牌数量 | `+0x21c` i32 | 对战中恒为 4 |
| 下一张队列指针 | `+0x220` → i32[n] | 队首就是下一张；打出的牌放回队尾 |
| 队列数量 | `+0x22c` i32 | 4 |

### 实体（`crai/reader/scan_entities.c`）
实体字段和旧 ARM 版笔记一致，**全部确认**：`+0x30` kind、`+0x78` side、`+0x7c/+0x80` x/y、`+0x84/+0x88` 次坐标、`+0xac` card id、`+0x120` 等级索引（等级 = 值 + 1）。

**重要发现：上面找到的 "player" 对象，本身就是国王塔实体。**
- vtable 相同（静态偏移 `0x1a50840`），kind 都是 13。
- 坐标：side 0 的在 (9000,3000)，side 1 的在 (9000,29000)。

| 类型 | vtable 静态偏移（运行时 vtable − libg 基址） | kind |
|---|---|---|
| 国王塔 / player | `0x1a50840` | 13 |
| 普通单位、公主塔 | `0x1a4fbb8` | 公主塔 13，部队 15 |

- 这两个 vtable 偏移可以当作"类型指纹"，用来快速筛选实体，不必再靠字段范围猜。
- 样例：side 1 有 Hog Rider（26000021，15 级），side 0 有 Night Witch（26000048，13 级）。
- side 1 一方的国王塔 16 级、公主塔 15 级，推测是用户本人；对手是训练营电脑。坐标在内存里是绝对坐标，side 1 在 y 值大的一侧。

### 全局入口与卡组（第 2 局训练赛，`ptrscan.c` / `probe.c` / `watch2.c` / `find_deck2.c`）
完整布局见 `configs/nulls_16.635.1.json`，那个文件是**唯一权威来源**。

```
roster      = *(*(*(libg+0x1b4b928) + 0x2a8) + 0x310)
player[i]   = *(roster + 0xe0 + 8*i)          // i=0/1，即该方国王塔实体
deck[i]     = *(roster + 0x88 + 8*i)          // 容器：+0x20 数据指针，+0x28 数量(8)
card(d)     = *(*(*(deck.data + 8*d)) + 0x10) + 0x40   // deck index d 的卡牌 ID（元素→wrapper→+0x10 卡牌对象）
```

- 本局中 player[0] 是 side 0（训练营电脑，13 级），player[1] 是 side 1（用户，16 级）。player[i] 和 side 的对应关系是否固定还**待确认**；目前按 player 对象的 `+0x78` side 字段区分。
- 用 `watch2` 记录的圣水扣减交叉核对 deck index → 卡牌：冰精灵(1)、圆木(2)、加农炮(3)、骷髅兵(1)，全部吻合。
- `player+0x288` i32[8] 是"首次出牌顺序"的卡牌 ID 列表，没出过的位置为 -1。**它不是按 deck index 排的**。
- `player+0x258` 是最近打出的卡牌对象（vtable `0x1a3bcf8`，ID 在 `+0x40`）。旧 x86 文档里"20 字节动作记录"的结构在这个版本不适用。
- `player+0x318` 是出牌序号，每出一张牌 +1。
- 出牌瞬间手牌槽短暂为 -1，约 10–50ms 后补上新牌。

### 第 3 局训练赛
- **全局路径 `libg+0x1b4b928 → +0x2a8 → +0x310` 跨局失效**：`a`、`b` 地址不变，但 `b+0x310` 不再指向 roster。
  - 改用读取器启动时扫描：先用 vtable 指纹找到双方国王塔，再找同时存放两者指针（`+0xe0/+0xe8`）且 `+0x88` 卡组数量为 8 的 roster。约 0.2–3 秒。
  - `ptrscan <pid> 4 400 roster` 本局找到 58 条静态路径，跨局是否稳定待下一局对比，结果在 `re/ptrscan_roster_2.txt`。
- **血量确认**：HP 访问函数在 `libg+0x108b474`（vtable 槽 `+0x120`）。
  - 条件：`byte[e+0x30] & 4` 且 `i32[e+0x24] >= 3`。
  - 读取：`comp = *(*(e+0x18)+0x10)`，当前血量 `i32[comp+0x10]`，最大血量 `i32[comp+0x14]`。
  - 实测国王塔 5832/5832（13 级）、7336/7728（16 级）。
- 实体都分配在 `[anon:libc_malloc]` 区域。实体列表容器还没确定，有 3 个候选数组（见 `re/whoref_1.txt`、`re/findptr_1.txt`）。
- **读取器 `crai/reader/cr_reader.c`**：
  - 实测约 25 帧/秒。普通帧 0.19ms；每 15 帧重扫一次 malloc 区找实体，耗时 120–260ms。
  - 待优化：把重扫放到独立线程，或者找到真正的实体列表。
- **点击标定**：落点会吸附到格子中心（坐标 x500）。画面有透视，要用单应矩阵，见 `scripts/calibrate.py` v2。第一轮标定样本不足，已作废。

### 点击控制与标定（第 4–9 局，大部分由脚本自动开训练营完成）
- **下牌必须用拖拽**（`input swipe` 从手牌槽拖到目标点）。
  - "点卡再点场地"会受到残留选中状态的影响：对已选中的卡再点一下是取消选中。
- 读取帧必须"只取最新"（`crai/reader/stream.py` 的 `LiveReader`）。逐帧消费会积压，处理慢时读到的是几十秒前的状态。
- 不能用"圣水 3 秒不变"判断对局结束：圣水满 10 时本来就不变。
- 落点吸附到格子中心。画面有透视；二次多项式模型比单应矩阵更准（留一误差中位约 31px）。
- 标定流程：
  1. `scripts/calibrate.py`：在空旷区域自动下牌，样本累积到 `re/calib_samples.json`；
  2. `scripts/fit_calib.py`：稳健拟合，输出 `configs/screen_1080x1920.json`；
  3. `scripts/verify_deploy.py`：按目标格子下牌并验证，同时追加样本。
- **精度：目标格命中 11/14，其余只偏 1 格（集中在后排）**。
- 自动化工具：`scripts/start_training.py`（结算 → 菜单 → 训练营 → 确定，并等待读取器确认开局）、`scripts/ui.py`（截图/点击/拖拽）。
- 训练营对手是"训练师奇达二世"（13 级）。主界面"对战"按钮是天梯，会改变奖杯。

### 实体列表、kind 含义、遗留对局（2026-11-20 晚）
- **实体列表**：`list = *(*(roster+0x8)+0x40)`，`+0x8` 数据指针，`+0x10` 容量，`+0x14` 数量。
  - 16 次采样，vtable 全扫描的实体 100% 都在列表里。
  - 列表中偶尔有其他类型对象，疑似法术或投射物，待研究。
  - 读取器优先读这个列表，读不到时再退回后台扫描。实测 29 帧/秒，p99 0.43ms。
  - 工具：`entlist.c`、`reach.c`、`verify_entlist.c`、`scripts/find_entlist.py`。
- **kind 含义**：12 = 未激活的国王塔，13 = 激活的塔，14 = 部署中，15 = 部队。识别塔要用 `card == -1`，不能只看 kind。
- **遗留对局**：对局结束后旧 roster 结构仍然有效，新对局还可能复用同一个地址。
  - 读取器：有多个候选时，选圣水在变化的那个；圣水冻结 3 秒（且不是都满）时重新定位。
  - 开局检测：对局对象地址变化，或出牌序号回落，才算新局。
- **坐标翻转**：约 18 局（3 局天梯加约 15 局训练营）己方都是 side=1，看来私服总把本地玩家放在 side=1。翻转代码保留作兜底，但**从未实际触发**。

### 回放指令注入（2026-11-21，已验证可行）
- **游戏内回放 = 客户端按指令列表现场重新模拟**。读取器能完整读到回放战局（单位、血量、双方圣水与手牌）。
- **出牌指令对象**（96 字节）：
  - `+0x00` vtable，值为 `0x4DED748`，即 libg+0x1a29748（libg 基址 0x33c4000 时）
  - `+0x0C` 生效 tick，`+0x10` 下达 tick（= 生效 −20）
  - `+0x18` 玩家标识（如 44679514 / 71299567）
  - `+0x28/+0x2C` 落点 x/y（内存绝对坐标）
  - `+0x38` 卡牌数据指针（卡牌 ID 在 +0x40）
  - `+0x48` 打包字段（同一张卡值相同，含义待查）
  - 工具：`list_cmds.c`（按 vtable 扫描）、`poke.c`（写 i32）、`dump_records.c`、`scan_cmds.c`
- **生命周期**：回放开播时整局指令一次性加载，**执行过的指令对象随即释放**，内存中只剩尚未执行的指令。
- **写入验证**：修改一条未来加农炮指令的 x（6500 → 11500，从左侧挪到右侧），回放结局从真实的"1:2 时间到"变成"对手 3 冠拆掉国王塔"，说明模拟按改后的指令执行。
- 注意：回放中按返回键会弹出"要返回主界面吗"并暂停播放，点取消后继续。
- **回放开局设置**（开播时读取，`dump_decks.c`、`scripts/replay_setup_probe.py`）：
  - 卡组元素（`roster+0x88/+0x90 → +0x20 数据 → 元素`）：
    - `+0x10` 卡牌数据指针
    - `+0x18` 等级索引（普通 15 / 稀有 13 / 史诗 10 / 传奇 7 都等于 16 级）
    - `+0x1C` 进化等级
    - `+0x24` 骷髅兵为 3，含义未知
  - 开局手牌和队列：player `+0x210` / `+0x220`（出牌序号为 0 时即可读写）。
  - 两个玩家标识分别对应 player[1]（44679514，用户）和 player[0]（71299567）。
- **指令打包字段 `+0x48` 已解码**，与 x86 文档的 action meta 一致：`费用 = v>>28`，`deck_index = ((v>>22)&0x3f)-1`，`variant = ((v>>4)&7)-1`，`type = v&0xf`，固定位 0x3C00。用户 7 张卡全部核对正确。
- **注入计划**：开播后、第一条指令执行前：
  1. 改双方卡组元素的卡牌指针和等级，关闭进化；
  2. 改开局手牌和队列；
  3. 按 tick 顺序改写全部指令对象（tick、玩家、x/y、卡牌指针、打包字段），多余的指令把 tick 设到对局结束后。
  - 任意卡的卡牌数据指针：扫描 vtable 为 card_vt 的全局卡牌对象，按 +0x40 的 ID 建表。

- 还没解决：怎么区分己方和对手；如何从全局变量稳定地定位到 player 对象，而不是每次全内存扫描（全扫一次约 783 MiB）。

## 离线引擎（2026-11-21，已跑通）
代码：`crai/probe/proxy_min.c`（代理 libsentry-android.so，root 替换，部署 `scripts/probe_min.ps1`）。
- **原生回放 JSON**：钩子 ReplayJsonSetter（`0xda1f90`，参数 2 是 libg 字符串：`+0` 缓存长度、`+4` 字节数、`+8` 内联或指针）抓到游戏自己的回放，样本 `re/native_replay/ladder_last.json`。解析后的对象存在 `this+0x88`（15 版是 `+0x78`）。
  - 结构：`battle`（deck0/deck1.sp[{d,l,el,pr}]、avatar0/1、location、hbd…）、`cmd`、`evt`、`endTick`、`rndSeed`。
  - `el`：1 = 进化，2 = 英雄。`pr` 含义未知（会编码进 pd 的 bit 17–18），不填也能正常运行。
  - 出牌指令 `ct=153`（15 版是 86）：`c.t`（下达 tick）、`c.t2 = t + 20`（生效 tick）、`idLo`（玩家 ID）、`px/py`、`sel.os`（卡牌 ID）、`sel.pd`。`ct=189` 带 `cgid`，疑似表情。
- **`sel.pd` 会被引擎校验并决定是否进化**：`费用<<28 | (卡组位置+1)<<22 | 形态位<<14 | 0x3C00 | 进化计数<<7 | 标志`。
  - 形态位：`0x20` 可进化，`0x40` 英雄，`pr<<3`。
  - 进化卡第 1..N 次出牌为普通，计数 1..N；第 N+1 次为进化版，计数 N+1、标志 1，然后计数归零（N = cycle_required，常见为 2）。
  - 英雄卡固定为形态位 `0x40`、标志 2。
  - pd=0 时指令全部被拒绝；去掉进化位时，指令能执行，但出的是普通版。
  - 编码器 `scripts/royaleapi_to_native.py: PdEncoder` 对 49 条真实指令 0 不符。
- **起手牌**由 `rndSeed` 洗牌决定，是固定的位置排列，与卡组内容无关；引擎保留 JSON 里的卡组顺序。种子 1795206595 下，side0 起手位置 `[5,0,2,3]`、队列 `[6,7,1,4]`；side1 起手 `[2,1,0,6]`、队列 `[4,7,3,5]`。
- `endTick` 不是硬性截止，对局按规则自然结束（含加时）。
- **流程**（照抄 16 版 NativeReplayRunner `0xd9ae04`）：
  1. 地点 tilemap 预热（`0xefe42c` → `0xf2edec` / `0x8ae750`）；
  2. `new(0x240)`（15 版是 0x230）→ ctor `0x11d1e68(m,1,ctxA,ctxB,0)` → setup `0x11d225c(m,1)`；
  3. 16 版新增：`new(0x20)` 监听器，`0x10cab40(obj)`，虚表 = `*(libg+0x1a9a0d0)+0x10`，`[+0x18]=0x4000000000`，`0x108d23c(*(m+0x40), &obj)`；
  4. JsonParse `0x139f838` → load `0x11d2dc4(m, root, 0, 0)`（返回 bool）；
  5. 循环 step `0x11d3174`，tick `0x11d32f0`（读 `+0x60`）。
- 世界对象 = `m+0xa8`（即读取器的 roster）；实体列表 = `*(*(world+0xe0)+0x10)`：`+0x8` 数据、`+0x10` 容量、`+0x14` 数量。
- 在我们自己的线程上运行，游戏主界面同时在跑，目前没有冲突。
- **速度：一整局（约 3000–5000 tick）0.2 秒左右，约为实时的 700 倍。**

### 离线引擎补充（2026-11-21 上午）
- 技能指令：`{"ct":189,"c":{"t","t2"(=t+20),"idHi","idLo","cgid"}}`，`cgid` 是场上英雄/冠军单位的对象 ID（实体 `+0x08`，形如 5000066）。15 版是 `ct=2`。
